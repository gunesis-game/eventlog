## Approved public API constraints
- `PrepareLog[TEvent, TChannel](ctx, newEvent, newChannel) (TEvent, TChannel, error)` with `newEvent func(chan<- func() error) TEvent` and `newChannel func(chan Event, chan *ChannelError) TChannel` (D-049, D-052).
- `Event` is `Fields() Fields` plus `Transaction() chan<- func() error`; `Channel` is `Fields() Fields`, `Notifications() <-chan Event`, `Errors() <-chan *ChannelError`.
- `ChannelError{Kind, Cause, Events}` with `ErrorKind` values `TransactionRefused`, `TransactionPanicked`, `InvalidState`, `CommitFailed`, `ReaderFailed`, `DeliveryFailed`, `WriteNotPermitted` (D-068).
- `Config`, `WithStorage` with `Local{Directory}` (D-068; `Web{SettingsFile, DeviceStateDirectory}` designed, not implemented), `FieldOf`, `FieldOfNullable`, `IdentityOf`, `ErrConfigAlreadySet`, `ErrConfigNotInitialized`, `ErrSchemaConflict`.
- No new public package functions (user rule); no public shutdown API; no execution-lock concept.

12. [ ] Multi-device operation and web storage (D-056 to D-071; design D-060 approved). Built in the increments below, in order. Each increment is one reviewable change: tests beside the code, the full local suite and `gofmt` clean, CI green on Linux and Windows for its SHA, the public API checked with `go doc`, and everything it makes redundant removed. Increments 12.1 to 12.6 need no Google services and are tested on local storage; 12.7 builds a Google services emulator, and 12.8 to 12.10 add the web provider, tested against it.
    1. [x] **Storage isolation and refused writes (D-068, D-072).** The file-system boundary carries `fs.ErrPermission` (HTTP 403) from backend to client. At start the store learns whether this device may write; if not, it opens read-only, and a transaction that changes an Event is rolled back and refused with the new ChannelError kind `WriteNotPermitted` under the prefix rule, while transactions that change nothing, reading, and replay continue; a permission error during a commit reports `CommitFailed` and switches later transactions to `WriteNotPermitted`. Tests: a backend refusing writes, through the real server and client; a read-only local directory where the platform allows it.
    2. [x] **Log and device layout (D-060, D-062).** Local storage becomes `<Directory>/eventlog/` with `log.json` (permanent log identity, created once) and this device's log under `devices/{deviceID}/`; the device identity is generated on first start and kept in the device state (inside the directory for Local). No migration: no log has been released. Tests: identity stable across restarts, recovery and compaction unchanged inside the device folder.
    3. [x] **Causal metadata (D-064).** Event records carry the writing device, the Channel's version vector, and a hybrid logical clock timestamp; the v1 schemas change in place. Tests: schema round-trip, clock monotonic under backwards wall-clock steps, vectors advancing per Channel only.
    4. [x] **Reading other devices' logs (D-060, D-067, D-070, D-073).** The store reads every device folder; other devices' logs are read-only and an incomplete trailing transaction there counts as not yet committed. Positions in another device's log are its per-Channel occurrence counts, resolved through its manifest and re-resolved after compaction or a missing file. Another device's damaged history keeps its valid prefix and is otherwise missing; detection only, with `HistoryMissing` reported in 12.5. Tests use a test-only second device writing into the same storage folder, with change events injected.
    5. [x] **Causal delivery, conflicts, and missing history (D-057, D-058, D-070, D-074).** Readers merge local and remote occurrences, delivering a remote one only after everything in its version vector; concurrent occurrences of one logical Event are reported on the error stream and the current state is the greatest hybrid logical clock timestamp with device identity as tie-break. Missing history in another device's log is reported once per affected Channel with the new kind `HistoryMissing`, and its dependents are held. When several occurrences are ready, the earliest clock reading goes first, with device identity breaking ties, so replay is deterministic. The conflict kind is `ConcurrentChange` (D-074). Tests: delivery order across devices, held dependents, deterministic convergence on every device.
    6. [x] **Remote changes in live instances (D-059, D-075).** Delivered remote occurrences go through the Channel's transaction processor, which sets the live instance's selected fields to the converged state without persisting; live instances always hold the converged state, this device's own history included, so after a restart they show the persisted state (D-075). Tests: a live Event updated by another device's commit, interleaved with local transactions.
    7. [x] **Google services emulator for tests.** A test-only, in-process emulator (`internal/googletest`) of the Google services the web backend calls, so tests run the production backend code unchanged against it, with only its service addresses changed: OAuth sign-in and token refresh for several accounts, including the seven-day expiry of Testing status; and the Drive v3 calls the backend uses, with Drive's observed behaviour: the creating account owns a file, a folder not shared with an account is not found (404), Viewers are refused writes, sharing roles inherited from the folder, ownership offers made by updating the owner's inherited permission and accepted with `transferOwnership`, after which the writer can edit but not trash, `appProperties` and `'<owner>' in owners` queries, ranged reads, whole-file re-uploads (no append), and trashed files readable by ID. It keeps its state on a real filesystem in a folder it is given (a temporary folder per test): each Drive file's content as a real file named by its file ID, and Drive's metadata (names, parents, owners, permissions, `appProperties`, trashed state, sizes) in a metadata file beside them, so large logs are stored as they would be, an emulator restarted over the same folder keeps its contents, and a failing test leaves inspectable files. It uses the Go standard library directly, not eventlog's `internal/filesystem`, so the yardstick shares no code with what it measures. Each behaviour has tests, written from what the feasibility checks observed (docs/research/drive-access-model.md). No stand-ins: every web-storage test goes through the emulator. It also carries web-storage benchmarks and performance tests, so they never spend Google quota: it counts requests and bytes per account and per call, so benchmarks report Google calls and bytes per operation for comparison with the free-tier quotas, and it can add a configurable delay per call to model network latency. No automated test, benchmark, or CI job calls real Google services; runs with real accounts are manual only. Firebase joins the emulator in 12.10, to the same standard.
    8. [ ] **Web storage and the Google Drive backend (D-061, D-065, D-068).** `Web{SettingsFile, DeviceStateDirectory}` and the settings file format; a Drive backend behind the boundary: loopback OAuth sign-in with the `drive` scope, refresh token in the device state, `*AuthorizationRequired` from `PrepareLog` and the `AuthorizationRequired` kind while running; the folder found by tag and owner with IDs cached; file operations mapped to the Drive API, with appends re-uploading 1 MiB segments and `Remove` moving files to the trash; Viewers mapped to `fs.ErrPermission`. Local and Web are the two implementations of the one `Backend` interface in `internal/filesystem` (the OS backend and the Drive backend), selected from the `WithStorage` choice; the interface gains the generic change-event stream (the OS backend sends none) and nothing else provider-specific. A test checks that no core package imports the provider, and the core's tests run against both backends, the Drive one through the emulator with several accounts. A short manual run with the two real accounts confirms sign-in and the folder.
    9. [ ] **Ownership handover (D-069).** The Drive backend offers ownership of each file it creates by setting `pendingOwner` on the owner's inherited permission; owner devices accept pending offers at start and on change events. Tests through the emulator; a manual run with both accounts.
    10. [ ] **Change notifications through Firebase (D-063, D-066, D-071).** First the emulator (`internal/googletest`) gains Firebase, to the same standard as Drive, so tests run the production notification code unchanged with only its service addresses changed: Firebase Authentication's exchange of a Google ID token for a Firebase token, its refresh, and expiry; the Realtime Database's REST writes and its server-sent event streams with Firebase's event types (`put`, `patch`, `keep-alive`, `cancel`, `auth_revoked`), the initial snapshot on connect, dropped and resumed connections, the 100-connection limit of the free plan, and the database being switched off; with counts of writes, connections, and streamed bytes per account. The board is kept on the same real filesystem, as a JSON file, so it survives an emulator restart. Each behaviour has tests. Then the board under `/eventlog/{logID}/devices/{uid}/{deviceID}`, streamed with server-sent events and turned into the boundary's generic file-change events; Google sign-in exchanged for a Firebase token; the members list synced from Drive sharing by owner devices, membership requests, and `ChangeEventsUnavailable`; the security rules published in the docs. Tests and benchmarks go through the emulator under the same no-stand-ins and no-real-quota rules, reporting board writes and streamed bytes per operation for comparison with the free plan's download allowance; whether the security rules are tested in Firebase's official emulator is settled before this increment. A manual run with both accounts.

[ ] **Moving a log between Local and Web (D-062).** Both backends hold the same `eventlog/` layout, so a log keeps its identity when moved; moving to Drive must also hand each file to the owner (D-069). Approach to be approved first, within the no-new-public-function rule: a documented manual copy, or eventlog importing an existing log itself.

## Known gaps and follow-ups
- The in-memory index and `index.json` grow with total history, and every process start replays full Channel history.
- The full benchmark catalogue (benchmarks.md) is not yet implemented.
- Coding-standard review of the final implementation is not yet done.
- Compaction and ownership handover conflict: compaction removes replaced segments by trashing them (D-067), but once a segment is handed to the owner (D-069) its writer can no longer trash it, as the ownership check observed and the emulator models. To be settled before 12.9.
